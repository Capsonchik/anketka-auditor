# Reactor Roadmap: Migration of map2.php to Next.js + FastAPI

## 1. Анализ legacy-кода (`map2.php`)

Файл `map2.php` — это монолитный PHP-скрипт, который выполняет роль API, контроллера и генератора представления (HTML/JS) одновременно.

### Ключевые функции:
1.  **Карта (YMaps JS):**
    *   Использование `ObjectManager` для кластеризации точек.
    *   Кастомные балуны (Balloon Content Layout) с HTML-таблицами и формами.
    *   Визуализация статусов через цвета маркеров и иконки кластеров.
    *   Drag-and-drop маркеров и изменение координат через балун.
2.  **Управление задачами (Tasks):**
    *   Загрузка задач с фильтрами (статус, проект, волна, локации, даты).
    *   Массовые действия (Bulk Actions): назначение аудиторов/координаторов, смена статусов, редактирование полей (легенда, стоимость).
    *   Синхронизация данных локации (`shop_id`, `lname`, `laddress`) между таблицами `answers`, `chartpoints`, `tmp_stat_total2`.
3.  **Система заявок (Claims):**
    *   Аудиторы подают заявки на "свободные" проверки.
    *   Координаторы/контролеры одобряют или отклоняют заявки.
4.  **Роли и права:**
    *   Разделение на Аудитора (`user_rights_id=1`), Координатора (9), Контролера (8) и Оператора (7/10).
    *   Аудитор видит только свои и "свободные" проверки.

### Проблемы текущего решения:
*   **SQL Injection:** Использование `mysql_real_escape_string` и конкатенации строк.
*   **Производительность:** Тяжелые запросы без пагинации и чанковинга на бэке.
*   **Тестопригодность:** 0% покрытия тестами, логика смешана с UI.
*   **Сложность поддержки:** Один файл содержит HTML, CSS, SQL и бизнес-логику.

---

## 2. Архитектура целевой системы

*   **Frontend:** Next.js 14+ (App Router), React 18+, TypeScript, Zustand (state), React Query (data fetching).
*   **Backend:** FastAPI, Pydantic V2, SQLAlchemy/SQLModel, Alembic.
*   **База данных:** MySQL/MariaDB (с поддержкой клиентских схем).

## 3. Дорожная карта реализации

### Этап 1: Backend (FastAPI)

**1.1. Типизация и модели данных (Pydantic)**
*   Создать модели `Task`, `TaskStatus`, `User`, `Location`, `TaskClaim`.
*   Определить схемы запросов (FilterTaskRequest) и ответов (TaskResponse, PaginatedTasksResponse).

**1.2. API Endpoints (REST)**
*   `GET /api/v1/tasks`: Получение списка задач.
    *   Поддержка пагинации (`offset`, `limit`).
    *   Поддержка фильтрации по статусу, проекту, дате, координатам (для карты).
*   `POST /api/v1/tasks/bulk`: Массовые действия.
    *   Принимает `task_ids` и `action` (assign_auditor, change_status, update_location).
    *   Использует транзакции для обновления связанных таблиц.
*   `POST /api/v1/tasks/{task_id}/assign`: Назначение конкретной роли (аудитор/координатор/контролер).
*   `GET /api/v1/tasks/claims/{task_id}`: Получение заявок на проверку.
*   `POST /api/v1/tasks/claims/{claim_id}/approve`: Одобрение заявки.
*   `POST /api/v1/tasks/claims/{claim_id}/reject`: Отклонение заявки.
*   `POST /api/v1/tasks/claim`: Подать заявку (для аудитора).
*   `GET /api/v1/filters`: Получение справочников для фильтров (волны, проекты, пользователи).

**1.3. Оптимизация SQL**
*   Реализовать функцию `sync_location_data`, аналог `map2SyncPublishedTaskLocation`.
    *   *Оптимизация:* Разбивать список ID на чанки (по 500-1000) и делать `INSERT/UPDATE` через `executemany` или `VALUES (...)` для избежания N+1 проблемы.
*   Добавить индексы для полей `user_task.status`, `user_task.user_id`, `location.shop_id`.

### Этап 2: Frontend (Next.js)

**2.1. Интеграция данных (Zustand + React Query)**
*   Создать хранилище `useMapStore` для состояния карты и выбранных задач.
*   Заменить моки в `entities/task` на реальные API-запросы.
*   Реализовать `useTasks` хук для получения данных с кэшированием.

**2.2. Реализация карты (MapPage)**
*   **Библиотека:** Использовать `react-yandex-maps` для интеграции с YMaps.
*   **Кластеризация:** Использовать `Clusterer` из YMaps.
*   **Балуны:** Вместо HTML-строк из PHP, написать React-компоненты для балунов:
    *   `TaskBalloon` (детали задачи, кнопки действий).
    *   `ClusterBalloon` (список задач внутри кластера).
*   **Синхронизация локации:** При смене локации в массовых действиях вызывать API и обновлять координаты маркеров.

**2.3. Фильтры и Таблица (TasksPage / Panel)**
*   Использовать `TanStack Table` для рендеринга таблицы задач.
*   Реализовать клиентскую сортировку и фильтрацию (если данных < 5000), иначе — серверную.
*   Встроить компонент `TaskFilters` (UI) в боковую панель карты.

**2.4. Массовые действия (Modals)**
*   Переписать модальные окна из `map2.php` на компоненты из `shared/ui/modal`.
*   Логика применения массовых действий через `useMutation` (React Query).

## 4. Сравнение логики и улучшения

| Функция | map2.php (Legacy) | Next.js + FastAPI (Target) | Улучшение |
|---|---|---|---|
| **Фильтрация** | POST-запрос, вся логика в PHP. | Гибридная: фильтры в URL (для шаринга) + состояние React. | Возможность поделиться ссылкой с фильтрами. |
| **Карта** | Глобальные переменные JS, `myGeoObjects`. | React State, `useEffect` для инициализации карты. | Устранение утечек памяти, реактивность. |
| **Массовые действия** | Цикл по ID в PHP, блокировка потока. | Асинхронные задачи (Celery/RQ) или чанкинг в FastAPI. | UI не зависает при обновлении 1000+ задач. |
| **Безопасность** | `mysql_real_escape_string`. | SQLAlchemy (Parameterized Queries) + Pydantic валидация. | Защита от SQL Injection и XSS. |
| **Синхронизация** | Прямой UPDATE по списку ID. | Транзакции + Upsert (INSERT ... ON CONFLICT). | Целостность данных, скорость. |
| **Заявки (Claims)** | Микс PHP логики и JS. | Явные API endpoints для CRUD заявок. | Чистота кода, возможность кэширования. |
| **Валидация** | `if ($value !== '')` | Pydantic Model Validation | Строгая типизация входных данных |
| **UI** | jQuery + HTML Strings | React Components (TypeScript) | Компонентный подход, переиспользование |

## 4.1. Упрощение и улучшения при миграции

Файл `map2.php` содержит огромную сложность ("God Script"), которая в современном вебе решается разделением ответственности. Ниже — подробный список того, что можно и нужно упростить/улучшить при переносе на Next.js + FastAPI, разбитый по категориям.

### 4.1.1. Архитектура: Разделение данных и отображения

**Сейчас (map2.php):**
Код генерирует HTML-строки прямо внутри PHP. Переменная `task_txt` собирается циклом `foreach` и содержит `<table>`, `<tr>`, `<td>`.

```php
// PHP генерирует HTML
$task_txt .= "<tr onclick='map2ToggleTaskRow(...)'>...";
```

**Как улучшить:**
*   **Чистый API:** FastAPI должен отдавать только JSON (список задач с полями: `id`, `lat`, `lng`, `status`, `score`).
*   **Рендеринг на клиенте:** Next.js сам строит таблицу и балуны.

**Плюсы:**
*   Можно легко добавить экспорт в Excel, PDF или мобильное приложение без переписывания логики на бэке.
*   Код HTML больше не перемешан с бизнес-логикой.

### 4.1.2. Производительность: Работа с большими объемами

**Сейчас:**
*   Загрузка всех задач в память браузера (`app.tasks`), даже если их 10 000.
*   Массовые операции (`map2SyncPublishedTaskLocation`) блокируют интерфейс на время выполнения SQL-запросов.

**Как улучшить:**

**Пагинация и Чанкинг:**
*   Карту загружать только видимый регион (bounding box).
*   Таблицу грузить постранично (Server-side Pagination) через FastAPI.

**Фоновые задачи (Async Jobs):**
*   Массовые действия (смена локации, назначение 100 аудиторов) делать через Celery (Python) или FastAPI `BackgroundTasks`.
*   Пользователь нажимает "Применить", видит тост "Обработка...", а сервер делает тяжелую работу в фоне.

### 4.1.3. Сложная логика синхронизации (Location Sync)

**Сейчас:**
Функция `map2SyncPublishedTaskLocation` — это "монстр". Она проверяет статусы, ищет таблицы в разных схемах (`answers`, `chartpoints`), делает дублирующие запросы и возвращает огромный массив отладочной информации.

**Как улучшить:**

**Выделить в отдельный сервис (Use Case):**
*   Создать класс `LocationSyncService` в FastAPI.
*   **Входящие данные:** `List[TaskId]`, `NewLocationId`.
*   **Выходные данные:** `SyncResult` (успешно/ошибка).

**Упрощение логики:**
*   Вместо кучи `if/else` для таблиц использовать ORM (SQLAlchemy).
*   Убрать возвращение отладочных SQL-запросов (`$total_rez["query_up"]=$query_up`) в продакшен.

### 4.1.4. Управление состоянием (State Management)

**Сейчас:**
Глобальные переменные JavaScript: `app.tasks`, `app.cur_page`, `app.map2SelectedTaskIds`. Это приводит к багам, когда данные в таблице и на карте рассинхронизируются.

**Как улучшить:**
*   **Zustand (или Redux Toolkit):** Единый источник правды.
    *   `useMapStore` хранит состояние карты.
    *   `useTasksStore` хранит данные задач.
*   **React Query:** Автоматическое кэширование и обновление данных при изменениях. Если вы назначили аудитора, React Query сам обновит данные в таблице и на карте.

### 4.1.5. Интерфейс и UX (User Experience)

**Сейчас:**
*   Огромная модальная форма с 20+ полями для массовых действий.
*   Сложная навигация по табам (Фильтр → Инструменты → Выбранные).

**Как улучшить:**

**Контекстные действия (Context Menu):**
*   Вместо одной большой формы — контекстное меню при выделении задач.
*   Кнопка "Назначить аудитора" открывает маленький поиск, а не целый блок настроек.

**Командная строка (Command Palette):**
*   Реализовать аналог `Ctrl+K` (как в VS Code) для быстрого поиска задач и выполнения действий.

**Реалтайм (WebSockets):**
*   Если координатор одобрил заявку, у аудитора на карте статус должен измениться мгновенно, без перезагрузки страницы.

### 4.1.6. Безопасность и Валидация

**Сейчас:**
*   Валидация на стороне PHP (`if ($task_id <= 0)`).
*   Явные SQL-инъекции через конкатенацию строк (хоть и с `mysql_real_escape_string`).

**Как улучшить:**

**Pydantic (Backend):** Жесткая типизация входных данных.
```python
class BulkUpdateRequest(BaseModel):
    task_ids: List[int]
    action: Literal['assign_auditor', 'change_status', 'update_location']
    location_id: Optional[int] = None
```

**Middleware (Permissions):**
*   Проверка прав (Роли: Auditor, Coordinator, Controller) делать на уровне маршрутов FastAPI, а не размазывать по функциям.

### 4.1.7. Что можно УДАЛИТЬ (Technical Debt)

**CSV Импорт ("Загрузка CSV"):**
*   В коде есть огромная логика загрузки CSV через `fgetcsv`. Это устаревший подход.
*   **Аналог:** Использовать готовые библиотеки (например, React Dropzone + CSV parser) или просто Excel-загрузку, которая валидируется на бэке.

**Устаревшие статусы:**
*   В коде есть сложные маппинги для "статуса 0" (Создана → Ожидает/Назначена).
*   **Аналог:** Можно упростить до `unassigned` (`null` user_id) и `assigned` (`user_id` есть).

**Генерация CSS в PHP:**
*   Цвета и стили генерируются прямо в HTML.
*   **Аналог:** Вынести в CSS Modules или Tailwind.

### 4.1.8. Итоговая схема упрощения

| Логика | Старое решение (PHP) | Новое решение (Next + FastAPI) |
|---|---|---|
| **Загрузка данных** | Загрузить ВСЁ в массив JS | Загрузить постранично + Bounding Box для карты |
| **Фильтрация** | Фильтрация в JS (`array_filter`) | Фильтрация в SQL (`WHERE status=...`) |
| **Смена локации** | Синхронный UPDATE таблиц | Асинхронная задача (Background Task) |
| **Заявки (Claims)** | Ручной AJAX запрос при клике | WebSocket событие при одобрении |
| **Валидация** | `if ($value !== '')` | Pydantic Model Validation |
| **UI** | jQuery + HTML Strings | React Components (TypeScript) |

### 4.1.9. Рекомендация для начала

Самое важное упрощение — это перестать генерировать HTML на бэке. Оставьте в `map2.php` (и его преемнике в FastAPI) только чистую JSON-логику. Это сразу уменьшит объем кода в 3-4 раза и сделает систему гибкой.

## 5. Детальные задачи по Backend (FastAPI)

1.  **Создать API для синхронизации локации (`/sync_location`):**
    *   Вход: `task_ids: list[int]`, `new_location_id: int`, `new_shop_id: str`.
    *   Логика:
        *   Получить данные локации (name, address).
        *   Обновить `user_task.location_id`.
        *   Обновить таблицы схемы клиента (`answers`, `chartpoints`, `tmp_stat_total2`) для опубликованных задач.
        *   Вернуть статус обновления для каждой задачи (успех/ошибка).
2.  **API для управления статусами и назначениями:**
    *   Проверка прав (Can User Assign Auditor?).
    *   Блокировка переназначения для статусов 1, 2, 3, 7 (как в `map2AuditorReassignmentLockedTaskIds`).
3.  **API для заявок (Claims):**
    *   `POST /claim`: Проверка, не занята ли задача, создание записи.
    *   `POST /approve`: Назначение аудитора, закрытие заявки.
    *   `POST /reject`: Удаление/закрытие заявки.
4.  **Экспорт в Excel:**
    *   Использовать `pandas` или `openpyxl` для генерации `.xlsx` на основе запроса фильтров.
