# Frontend Паттерны

## 2.1. Компонентные паттерны

### Presentational и Container (умные/глупые компоненты)

**Presentational** компоненты отвечают только за отображение (UI), получают данные через props.

**Container** компоненты содержат логику, состояние, обращаются к сторам/API и передают данные в презентационные.

**Применять:** когда нужно отделить бизнес-логику от визуала для переиспользования или тестирования.

**Не злоупотреблять:** в небольших компонентах разделение избыточно.

### Render Props / Функции как children

Используй, когда компонент должен предоставить гибкий способ рендера, зависящего от его внутреннего состояния.

Предпочитай современные альтернативы (хуки), если они решают ту же задачу проще.

### Higher-Order Components (HOC)

Применяй для сквозной функциональности (логирование, авторизация, работа с данными).

Старайся заменять HOC на хуки, если это возможно.

Именуй HOC с префиксом `with`: `withAuth`, `withLoader`.

### Хуки (Hooks)

Предпочтительный способ для логики с состоянием и побочными эффектами.

Выноси переиспользуемую логику в кастомные хуки: `useAuth`, `useWindowSize`.

Хуки должны следовать правилам:
- Вызываться только на верхнем уровне
- Только из React-функций

---

## 2.2. Паттерны управления состоянием

### Flux / Redux pattern

Если используется глобальный стор (Redux, Zustand):
- Однонаправленный поток данных
- Только экшены изменяют состояние
- Селекторы для чтения данных
- Асинхронные операции через thunk/saga или в хуках

Не смешивай локальное и глобальное состояние без необходимости.

### Observer (наблюдатель)

Применяется для событийных коммуникаций. В современном React часто заменяется колбэками или контекстом.

### Provider (контекст)

Используй React Context для передачи данных глубоко в дерево без проп-дриллинга.

Не злоупотребляй контекстом — он вызывает ререндеры всех потребителей при любом изменении.

---

## 2.3. Паттерны работы с данными

### Repository / Data Service

В слое `shared/api` или `entities/*/api` выноси логику запросов к API в отдельные сервисы.

**Пример:**
```typescript
userApi.fetchProfile()
productApi.getList()
```

Компоненты не должны зависеть от деталей HTTP.

### Adapter / Mapper

Если данные из API приходят в неудобном формате, создавай адаптеры (функции-трансформеры).

Размещай в `shared/lib/adapters` или внутри модели слайса.

## 3. Антипаттерны (чего избегать)

### God Object (божественный объект)
Не создавай компоненты или модули, которые знают и делают слишком много. Разделяй ответственность.

### Spaghetti Code (спагетти-код)
Не допускай запутанных связей и циклов зависимостей. Следуй правилам FSD.

### Copy-Paste программирование
Не дублируй код. Выноси повторяющуюся логику в `shared` или кастомный хук.

### Магические числа/строки
Все константы должны быть вынесены в `config` или константы.

### Смешивание слоёв
Обращение к API напрямую из UI-компонента без прослойки — недопустимо.

---

## 4. Компоненты

### Функциональные компоненты
- Использовать arrow functions: `const Component = () => {}`
- Избегать function declaration
- Типизировать пропсы через интерфейс

### Хуки
- Custom hooks с префиксом use: `useAuth`, `useFetch`
- Хуки вызывать на верхнем уровне
- Возвращать объект с понятными ключами
- Custom hooks выносить в `shared/lib/hooks/`

---

## 5. Работа с состоянием

### useState
- Простое: `const [count, setCount] = useState(0)`
- Сложное: через useReducer

### Context
- Создавать с дефолтным значением
- Провайдер с понятным именем: `AuthProvider`
- Хук с проверкой: `useAuth()` с throw если вне провайдера

---

## 6. Обработка событий

### Именование
- Префикс handle: `handleClick`, `handleSubmit`, `handleKeyDown`
- Типизация событий: `React.MouseEvent`, `React.ChangeEvent`

### Доступность (a11y)
- Keyboard support: Enter и Space
- role, tabIndex, aria-label
- onClick и onKeyDown вместе

---

## 7. Рендеринг

### Условный
- Early return для сложных условий
- Тернарный для простого
- && для показа/скрытия

### Списки
- Уникальные ключи: `key={item.id}`
- Не использовать индекс как ключ

---
