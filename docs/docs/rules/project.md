# Правила проекта

## 1. Сохранение существующей функциональности
Не изменяй работающий код без явной необходимости. Если код выполняет свою задачу и не содержит ошибок, не вноси в него правки.

Не удаляй комментарии, пояснения и документацию, если они не противоречат новым требованиям.

Не ломай обратную совместимость — изменения не должны нарушать работу других частей системы.

## 2. Осознанность изменений
Прежде чем предложить изменение, убедись, что оно действительно улучшает код (читаемость, производительность, безопасность).

Если изменение может затронуть другие модули, предупреди об этом и предложи план проверки.

Для рефакторинга сначала предложи обсудить, затем действуй.

## 3. Документирование кода
При создании функций или алгоритмов добавляй подробные комментарии и JSDoc с примерами использования на русском языке.

Формат JSDoc:
- Описание назначения функции
- @param — описание параметров с типами
- @returns — описание возвращаемого значения
- @example — пример использования на русском

## 4. Коммуникация и запрос уточнений
Если задача сформулирована неоднозначно — запроси уточнение, прежде чем действовать.

Объясняй свои действия кратко и понятно, особенно если предлагаешь серьёзные изменения.

Если предполагаешь несколько вариантов решения — опиши их плюсы и минусы.

## 5. Размер компонентов
Компонент не должен превышать **350 строк** кода (без учёта пустых строк и комментариев).

Если компонент больше 350 строк:
- Выдели логику в кастомный хук (`hooks/useComponentLogic.ts`)
- Раздели UI на подкомпоненты
- Создай отдельную папку с модульной структурой:
  ```
  component-name/
  ├── component-name.tsx
  └── component-name.module.scss
  ```

Признаки того, что компонент нужно разделить:
- Несколько зон ответственности
- Сложная условная логика
- Дублирование кода внутри компонента
- Более 5-7 пропсов
