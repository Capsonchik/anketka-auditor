# Архитектура проекта

## Общие принципы
- Next.js App Router — основа архитектуры
- Разделение по фичам (feature-based)
- Изолированные модули

## Структура проекта
src/
- app/ — Маршруты и страницы
- components/ — Переиспользуемые компоненты
- features/ — Функциональные модули
- lib/ — Утилиты и хелперы
- types/ — TypeScript типы

## Компоненты
- Функциональные компоненты с хуками
- Разделение на UI и логические компоненты
- Модульные стили (*.module.scss)

## Управление состоянием
- React Context для глобального состояния
- Локальное состояние через useState/useReducer
- Избегать избыточного состояния

## Работа с данными
- Серверные компоненты для fetching
- Клиентские компоненты для интерактивности
- TypeScript для типизации данных

# Правила архитектуры FSD (Feature-Sliced Design)

## 1. Общая структура
Проект организован по методологии Feature-Sliced Design. Основные слои (снизу вверх):

- **shared** — переиспользуемые утилиты, UI-компоненты, API-клиенты, константы, helpers.
- **entities** — бизнес-сущности (пользователь, продукт, заказ и т.п.).
- **features** — пользовательские сценарии (авторизация, добавление в корзину, фильтрация).
- **widgets** — композиционные блоки, собирающие фичи и сущности в самостоятельные части (шапка, сайдбар, карточка товара).
- **pages** — страницы приложения, композиция виджетов.
- **app** — инициализация приложения, глобальные стили, провайдеры, роутинг.

> Слой processes используется редко и опционален. Придерживаемся шести основных слоёв.

## 2. Слайсы (сегменты) внутри слоёв
Каждый слайс (например, entities/user, features/auth) может содержать следующие сегменты:

- **ui** — компоненты, относящиеся только к этому слайсу.
- **model** — бизнес-логика (store, actions, reducers, hooks).
- **lib** — вспомогательные функции для слайса.
- **api** — запросы к API, специфичные для слайса.
- **config** — конфигурация слайса (константы, enum).
- **types** — TypeScript-типы (если не вынесены в model).

Необязательно использовать все сегменты, но структура должна быть единообразной.

## 3. Правила зависимостей (импортов)

### 3.1. Направление зависимостей
Строго сверху вниз: слой может импортировать только те слои, которые находятся ниже него.

| Слой | Может импортировать |
|------|---------------------|
| app | все слои |
| pages | widgets, features, entities, shared |
| widgets | features, entities, shared |
| features | entities, shared |
| entities | shared |
| shared | только внешние библиотеки |

### 3.2. Импорты между слайсами одного слоя
- **features** может импортировать другой features, но это повышает связанность. Предпочтительнее выносить общую логику в entities или shared.
- **entities** могут импортировать другие entities (например, entities/order зависит от entities/user). Это допустимо.
- **shared** не должен импортировать другие слайсы shared — всё общее должно лежать в одном месте.

### 3.3. Запрещённые импорты
- ❌ Нельзя импортировать из вышележащих слоёв (например, entities не может импортировать features).
- ❌ Нельзя создавать циклические зависимости (A → B → A).

### 3.4. Публичное API (index.ts)
Каждый слайс должен объявлять свой публичный интерфейс через файл index.ts, который реэкспортирует только то, что разрешено использовать другим слайсам/слоям.

Внутренние модули (ui/*, lib/*) не должны импортироваться напрямую извне — только через индекс.

**Пример:**
```typescript
// entities/user/index.ts
export { UserCard } from './ui/UserCard';
export { userModel } from './model';
export type { User } from './types';
```

## 4. Организация файлов и папок
- Имена слайсов — в единственном числе, kebab-case (например, product-card, auth-by-phone).
- Сегменты внутри слайса — всегда папки с именами: ui, model, lib, api, config, types.
- Файлы внутри сегментов именуем в kebab-case (например, user-card.tsx, use-auth.ts).

## 5. Рефакторинг и перемещение кода
- Если код используется в нескольких местах одного слоя — вынести в shared или поднять в entities (если это сущность).
- Если фича становится слишком сложной — разбить на под-фичи внутри features.
- Не дублировать логику: всегда стремиться к единственному источнику правды.

## 6. Тестирование
- Тесты для слайса размещать рядом с кодом: model/__tests__, ui/__tests__.
- Мокать зависимости из нижних слоёв при тестировании вышележащих.

## 7. Что делать, если правило нарушает текущий код
Если в существующем коде есть нарушения зависимостей:
1. Предупредить о нарушении.
2. Предложить план исправления: либо переместить код в правильный слой, либо создать новый слайс.
3. Не вносить изменения, ломающие работоспособность, без согласования.

## 8. Проверка зависимостей
Использовать ESLint plugin @conarti/feature-sliced или @feature-sliced/eslint-config для автоматической проверки правил импортов.

## 9. Пример правильного импорта

```typescript
// ✅ pages/profile/index.ts
import { ProfileWidget } from 'widgets/profile';
import { useAuth } from 'features/auth';
import { User } from 'entities/user';

// ✅ features/auth/model.ts
import { api } from 'shared/api';
import { User } from 'entities/user';

// ❌ entities/user/ui/UserCard.tsx
import { AuthButton } from 'features/auth'; // Нельзя: entities не может импортировать features
```
